# Data Model and Limits

`runs` records mode, Seoul target date, timezone-aware start/end timestamps, status, counts, and sanitized error data. `facility_results` records `SUCCESS`, explicit `EMPTY`, or `FAILED` per facility. `observations` stores run id, observation timestamp, Seoul reservation date, facility, timezone-aware start/end, raw and normalized department, student level, optional source reservation id, and optional source status. Live own `data.room` rows start with raw and normalized department `도전탐색과정` and student level `UNDERGRADUATE`, independent of account identity. `roomOther` retains its `DEPT_NM` and `GROUP_NM` classification. No name, student id, contact data, grade, or inferred cancellation field exists.

A fully `SUCCESS` collection replaces prior `observations` and `facility_results` for its `(target_date, mode)` with the current run's rows. `runs` retains every attempt as audit history. `PARTIAL`, `FAILED`, and `AUTH_REQUIRED` runs never prune prior data. The snapshot export selects all observations from the latest successful or explicit-empty result for each `(target_date, facility_id)`. A failed later facility result never replaces an older successful snapshot. It does not sum observations across runs.

`identity_basis` is `SOURCE_ID` when the source provides a stable reservation id; otherwise it is `OBSERVED_FIELDS` and `comparison_key` is a documented SHA-256 fingerprint of observed facility, Seoul date/times, department, level, and source status. Neither fallback key nor source id has a database uniqueness constraint: identical-looking separate reservations are retained, and changed times are not declared new reservations. The collector does not infer cancellation when a row disappears.

Fixture missing end time remains SQL `NULL`. Live API rows are occupied one-hour slots numbered 0 through 23, so a 23:00 row ends at 00:00 on the next Seoul date. Live `EMPTY` is meaningful only after the bearer-token authentication probe, facility-list validation, and room payload validation. A malformed room is `FAILED` without discarding successful facilities.

Each `collect-once` captures one Asia/Seoul start timestamp and uses its date for the run ledger, live requests, and stored reservations. It collects only that current date, so it does not collect future or missed dates. Status reporting and runs distinguish successfully observed zero-result dates from failed or missing dates. The observable page is a snapshot, not a complete history: missed days cannot be recovered, reservation records do not prove actual use or study time, users are not unique, and no academic-performance inference belongs in this data. Free-text remarks and account identity fields are never persisted.
